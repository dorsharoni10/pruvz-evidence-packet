# Changelog

All notable changes to the Public Evidence Packet format and this repository are recorded here. Format releases follow the policy in [`docs/VERSIONING.md`](docs/VERSIONING.md).

## 1.6.1 — 2026-09-01

**PATCH (verifier bug fix — the packet format, the vectors and the package surface are unchanged)** — found by the first end-to-end live acceptance of the full evidence chain against a public timestamp authority (product PRUVZ-102). Packets keep declaring `packetFormatVersion: "1.5.0"`.

- **Fixed: the npm verifier refused genuine DigiCert timestamp tokens as `ANCHOR_UNTRUSTED_AUTHORITY`.** DigiCert's timestamp responder embeds, beside the chain that ends at the self-signed *DigiCert Trusted Root G4*, a second copy of that root cross-signed by *DigiCert Assured ID Root CA*. `lib/anchor-authority.mjs` handed every embedded certificate to pkijs's path builder, which selects issuers by name; the cross-signed copy displaced the root the caller had pinned and the path ran on towards an issuer nobody pinned — "no valid certificate paths found" for a token whose chain to the pinned root was intact. An embedded certificate that carries a pinned root's name is now excluded from the intermediate candidates: the pinned root is the anchor by definition, and a path must still end in a pinned root, so the change admits nothing it did not admit before. This is the behaviour the Python and .NET verifiers already had (both terminate at a pinned root before consulting embedded certificates, and both reach `FULLY_VERIFIED` on the same bundle); the three runtimes now agree on it. Regression test: a minted authority that embeds a cross-signed look-alike of its root (`test/helpers/mint.mjs`, `crossSignedRoot`), verified `FULLY_VERIFIED` against the real root and still `NOT_VERIFIED` against a stranger's.
- Nothing else changed. The Python and .NET packages are re-published at 1.6.1 solely to keep the one version stream (`docs/VERSIONING.md` release step 6).

## 1.6.0 — 2026-08-31

**MINOR (package surface only — the packet format is unchanged)** — the Python and .NET verifiers become first-class installable products (product PRUVZ-101). Packets keep declaring `packetFormatVersion: "1.5.0"`; there is no `schema/v1.6.0/` directory and no schema or vector changed. This is the first release where a repository MINOR is additive to the *published package surface* rather than to the packet format.

- **New: PyPI distribution.** `pip install pruvz-evidence-packet` installs the Python verifier — the exact `conformance/python/pruvz_verifier/` sources the three-runtime conformance suite exercises, now with a `pyproject.toml` and a `pruvz-verify` console entry point mirroring the npm CLI's argument surface and exit codes (`0`/`3`/`1`, `2` for usage or unusable input). The published schema releases and the `verifier/v1` golden vectors ship as package data, so the installed package verifies bundles completely offline with no repository clone.
- **New: NuGet distribution.** The .NET verifier sources moved from `conformance/dotnet/` into a library project [`dotnet/Pruvz.EvidencePacket/`](dotnet/Pruvz.EvidencePacket/) (namespace `Pruvz.EvidencePacket`, schemas and vectors embedded as resources); the conformance harness now references that library and behaves exactly as before. Two packages publish per release: `Pruvz.EvidencePacket` (library) and `Pruvz.EvidencePacket.Tool` (a `pruvz-verify` dotnet tool with the same argument surface and exit codes).
- **One version stream, enforced mechanically.** npm, PyPI, both NuGet packages and the git tag carry the identical version: [`bin/check-versions.mjs`](bin/check-versions.mjs) asserts it in `npm test` and the release workflow re-checks it against the dispatched tag. Because registries share no transaction, a release version is Complete only when every channel has published; each channel's publish is idempotent, and a partial registry failure is resumed by re-dispatching the same tag — never a new version, never rebuilt artifacts ([`docs/VERSIONING.md`](docs/VERSIONING.md) release step 6).
- **The conformance gate now also judges the built packages.** CI and the release workflow run the Python harness against the *installed wheel* and the .NET harness against the *restored nupkg* (`PRUVZ_CONFORMANCE_PACKAGED=1`, with any schema fallback to the repository forbidden and the loaded assembly proven byte-identical to the restored package), then run the isolated offline acceptance: both installed CLIs must reach `FULLY_VERIFIED` on the golden bundle inside `--network none` containers containing no repository clone ([`conformance/isolated/`](conformance/isolated/)).
- **Release workflow reworked** ([`.github/workflows/release.yml`](.github/workflows/release.yml)): still human-dispatched from an immutable tag that must be an ancestor of `main`, still gated by the full conformance suite on the tagged bytes — now building and verifying all four artifacts before the first publish, then publishing npm (Trusted Publishing with provenance; the 1.5.1 bootstrap token block is gone), PyPI (Trusted Publishing with attestations, `skip-existing`) and NuGet (`--skip-duplicate`; Trusted Publishing where enabled, otherwise a scoped push-only key). One-time account/publisher setup is recorded in [`docs/CONFORMANCE-SUITE.md`](docs/CONFORMANCE-SUITE.md) §6.

## 1.5.1 — 2026-08-31

**PATCH** — the adversarial cryptographic conformance suite with two additional full, independent verifier implementations (product PRUVZ-97). The packet format is unchanged: packets keep declaring `packetFormatVersion: "1.5.0"`.

- **New: the conformance suite** — [`docs/CONFORMANCE-SUITE.md`](docs/CONFORMANCE-SUITE.md) and the published adversarial vectors [`conformance/v1/golden-vectors.json`](conformance/v1/golden-vectors.json): 35 signed bundles, 3 raw byte strings and 41 attack-matrix cases covering mutation, normalization equivalence, serialization ambiguity (duplicate member names are refused as unusable input), replay across tenant/action/evidence, key substitution and misuse, rotation and the back-dated compromise boundary, registry rollback and fork against held state, Merkle deletion/reordering/insider insertion, corrupted proofs, checkpoint fork/rollback/stale history, anchor receipt swaps and corrupted token signatures, assurance-profile downgrades and mutations, truncation, and retained-proof honesty. Stateful cases are multi-step with pinned intermediate state. `conformance/v1/` is immutable like every released vector directory; the minting script is committed for provenance only.
- **New: two additional independent verifiers.** A .NET 8 implementation ([`conformance/dotnet/`](conformance/dotnet/), platform crypto + pinned `JsonSchema.Net`, no `pruvz-core` code) and a Python implementation ([`conformance/python/`](conformance/python/), hash-pinned `cryptography`/`asn1crypto`/`jsonschema`) each implement the complete proof chain — canonicalization, ES256, trust-registry lifecycle and history, Merkle proofs, checkpoint acceptance with held state, anchor bindings **and RFC 3161 half two** — and can independently reach `FULLY_VERIFIED`. [`bin/conformance-compare.mjs`](bin/conformance-compare.mjs) asserts every runtime equals the golden expectations and that all runtimes equal each other over the entire normalized output; no harness reads an expectation to produce its answer.
- **Fixed (found by the suite): multi-version chain re-verification.** `acceptChain` refused a served full history (`[v1, v2]`) against state already holding `v2` as `REGISTRY_ROLLBACK`, making every second run of the CLI's own `--state` workflow fail on a multi-version registry. History below the held **state** watermark is now verified but never judged as rollback; an out-of-order document inside one served chain, and a chain whose newest document is older than the held version, stay `REGISTRY_ROLLBACK` ([`docs/TRUST-REGISTRY.md`](docs/TRUST-REGISTRY.md) §8 clarified).
- **Fixed (found by the suite): anchor half-two reason codes drifted from the specification.** `lib/anchor-authority.mjs` emitted `ANCHOR_RECEIPT_SIGNATURE_INVALID` / `ANCHOR_AUTHORITY_UNTRUSTED`; the codes [`docs/ANCHORING.md`](docs/ANCHORING.md) §10 and the immutable `anchoring/v1` vectors define are `ANCHOR_SIGNATURE_INVALID` / `ANCHOR_UNTRUSTED_AUTHORITY`, and the implementation now emits them. `verifier/v1` (immutable) pinned the drifted signature code in one case; the recorded erratum in [`docs/VERIFIER.md`](docs/VERIFIER.md) governs replays, and `conformance/v1` pins the corrected code.
- **Hardened: duplicate JSON member names are unusable input.** One byte string that parses as two different documents is refused before parsing by the CLI ([`lib/json-guard.mjs`](lib/json-guard.mjs)) and by all three harnesses. Member equality is decided on **decoded** names, so a duplicate cannot hide behind an escape spelling (`"\u0061"` is `"a"`).
- **Distribution decision recorded** ([`docs/VERSIONING.md`](docs/VERSIONING.md), [`docs/CONFORMANCE-SUITE.md`](docs/CONFORMANCE-SUITE.md)): the package becomes `@pruvz/evidence-packet`, published to npm from the reviewed git tag with 2FA and provenance; one version stream (npm ≡ tag ≡ repository release, independent of `packetFormatVersion`); the repository stays cloneable and authoritative; .NET and Python verifiers stay repository/CI-only.
- CI now runs all three harnesses and the three-way comparison on every change; `npm test` replays the conformance suite through the Node implementation.

## 1.5.0 — 2026-08-31

**MINOR** — the packet becomes independently verifiable from its own bytes, and the independent offline verifier ships (product PRUVZ-88). Consumers reading `1.4.0` packets keep working on `1.5.0` packets if they ignore fields they do not recognize; `1.5.0` packets do not validate against the `1.4.0` schema (the schemas are strict by design).

- `schema/v1.5.0/` — new format release: every evidence-timeline item now also exposes the four remaining fields the canonical evidence-item commitment binds — `runId`, `schemaVersion`, `clientOperationId` and `payloadMetadata` (a flat string-to-string map, minimized at write time per the product’s read-back allowlist). Without them the commitment digest a seal names could not be recomputed from the packet, and the content dimension of verification would be permanently unverifiable. The action schema is unchanged.
- **New: the independent offline verifier** — the specification [`docs/VERIFIER.md`](docs/VERIFIER.md), the reference implementation [`lib/verify.mjs`](lib/verify.mjs) (with [`lib/anchor-authority.mjs`](lib/anchor-authority.mjs), anchor half two over `node:crypto` + `pkijs`), the CLI `npm run verify` ([`bin/verify.mjs`](bin/verify.mjs)), the bundle composer `npm run bundle` ([`bin/bundle.mjs`](bin/bundle.mjs)) and the published golden cases [`verifier/v1/golden-vectors.json`](verifier/v1/golden-vectors.json). One entry point composes every published layer over an exported bundle and answers with a dimensional report — verdict `FULLY_VERIFIED` / `PARTIALLY_VERIFIED` / `NOT_VERIFIED`, per-dimension statuses, machine-readable reason codes and human explanations. Missing material weakens and never passes; presented material that fails verification is a refusal, never a downgrade; a cost-gated capability the producing deployment did not run is reported honestly as absent and can never yield a full verdict.
- **Anchor verification half two is now implemented here**, closing the delegation that `1.4.3` published: CMS signature verification, the sole and critical timestamping purpose, certificate validity at the token’s own `genTime`, a chain to caller-pinned roots, and the policy allowlist. The published `runtimeDivergence` boundary is pinned at bundle level: the altered-signature token still binds, and the verifier refuses it.
- **Held verifier state** (`--state`) continues the registry and log acceptance rules across runs: rollback and fork presentations become refusals, a historical export is reported unconnected and never regresses the held state, only a checkpoint verified under the pinned registry ever enters that state, and state established under one pin — or handed over in any shape a previous run did not return — is refused rather than reinterpreted.
- The seven synthetic valid examples now declare format `1.5.0` and carry the four new fields on every item; the invalid examples authored against earlier formats keep declaring theirs (`disagreeing-exact-amount` moves to `1.5.0` with its rule intact). The captured conformance packet is unchanged and still declares the format of the run it was captured from. The validator supports all six formats.
- `verifier/v1/` is immutable exactly like a released schema directory and is protected from end-of-line conversion in [`.gitattributes`](.gitattributes). The adversarial conformance breadth and the mandatory second-runtime verifier that must reproduce every golden case exactly are the follow-up (product PRUVZ-97).

## 1.4.3 — 2026-08-30

**PATCH** — the packet format is unchanged and packets keep declaring `packetFormatVersion: "1.4.0"`. This release adds a specification, a reference implementation and golden vectors that sit beside the packet format rather than inside it (product PRUVZ-96, privacy-safe external anchoring).

- **New: the external anchoring specification** — [`docs/ANCHORING.md`](docs/ANCHORING.md), the reference implementation [`lib/anchoring.mjs`](lib/anchoring.mjs) and the published cross-runtime golden vectors [`anchoring/v1/golden-vectors.json`](anchoring/v1/golden-vectors.json). A signed checkpoint (`{ checkpoint, signature }`) or a signed trust-registry document (`{ manifest, signatures }`) is witnessed outside the deployment that produced it, under a sixth and seventh domain-separation tag (`pruvz.ai/log-anchor`, `pruvz.ai/trust-registry-anchor`). `anchoring/v1/` is immutable exactly like a released schema directory.
- **A 32-byte blinding nonce is part of the imprint**, so the 32 bytes that reach a witness are opaque: two authorities cannot tell they witnessed the same subject, a public observer cannot dictionary-test a candidate subject against a published imprint, and the imprint's opacity rests on the anchoring format rather than on a property of whatever happens to be inside the subject. The nonce is allocated once per anchor and **never regenerated** — a retry must present the same bytes, so that at-least-once delivery converges on one witnessed value. It is distinct from the RFC 3161 request nonce, which is fresh per request and is the only other value that reaches the authority; the specification tabulates the two so they cannot be conflated.
- **Only aggregate subjects may be anchored.** There is deliberately no per-record and no per-tenant anchor: a witness receiving one anchor per record would learn the shape of a tenant's activity without ever receiving an identifier. The residual leak that remains — a public authority learns how many checkpoints a deployment issued and when — is stated in the specification rather than omitted from it.
- **The trust-registry witness fills the seam left empty by 1.4.1.** A receipt lands in `attestations.witnesses`, outside the signed manifest, which is why the anchored subject excludes attestations: a subject that included them could never be witnessed. The registry's own rule is deliberately not weakened — `acceptChain` still ignores attestations entirely, rollback, fork and substitution stay decided by the signed manifest chain alone, and a witness can never rescue a manifest the chain refuses.
- **Verification is specified in two halves, and the boundary is published as a vector.** Half one binds a receipt to its subject; half two — CMS signature verification, the timestamping extended key usage, certificate validity *at `genTime`*, a chain to a **pinned** root rather than an ambient trust store, and the policy — is delegated to platform implementations under this repository's rule against home-grown cryptography. The reference implementation does half one and says so in its own result (`authorityVerified: false`).
- **The vectors distinguish agreement from required disagreement.** `bindingCases` and `refusals` are the agreement points, where every conformant runtime must behave identically. A new `runtimeDivergence` section carries the one case where they must *not*: a token with altered signature bytes still **binds** — its `messageImprint` is untouched — so a half-one implementation accepts it and a half-two implementation must refuse it. It is deliberately not filed as a binding case, because publishing it as agreement would misstate what half one establishes. The section also records that on some platforms the halves are not separable at the token level (.NET's `Rfc3161TimestampToken.TryDecode` verifies the CMS signature while decoding and returns false for a bad one), so such a runtime must still refuse but may report a different code — and names which codes are acceptable.
- **The receipt vectors are real.** Three genuine RFC 3161 tokens from a public timestamp authority are published as received, over the published imprints, including one under SHA-512 that must be refused as an unsupported suite. They embed the authority's certificate chain and cannot be regenerated. Refusals cover binding mismatch, a token from another subject, a mismatched nonce, truncated and structurally corrupted tokens, an unknown version, malformed records, and a pending or failed anchor presented where one was required — which can never yield a full verdict.
- **Retention is reconciled rather than assumed away.** Nothing deletable is ever anchored, so no external record can make deletion impossible; what survives a deletion is a proof that *some* bytes existed at a time. The specification states in the format itself that a commitment is **not** automatically non-personal data and that deleted payload must never be described as recoverable.
- **A packet still carries no anchor, no receipt and no witness time.** Anchors are fetched from the issuing deployment, exactly like seals, proofs and checkpoints; the schema releases are untouched. The `README.md` claim that external anchoring is not implemented was replaced with the precise statement: the format is specified, and whether a deployment anchors is that deployment's configuration.

## 1.4.2 — 2026-08-30

**PATCH** — the packet format is unchanged and packets keep declaring `packetFormatVersion: "1.4.0"`. This release adds a specification, a reference implementation and golden vectors that sit beside the packet format rather than inside it (product PRUVZ-87, append-only authenticated history and Merkle inclusion/consistency proofs).

- **New: the append-only evidence log specification** — [`docs/EVIDENCE-LOG.md`](docs/EVIDENCE-LOG.md), the reference implementation [`lib/evidence-log.mjs`](lib/evidence-log.mjs) and the published cross-runtime golden vectors [`evidence-log/v1/golden-vectors.json`](evidence-log/v1/golden-vectors.json). Every seal becomes a leaf of a Merkle tree in the published Certificate Transparency construction (RFC 6962 §2.1 / RFC 9162 §2.1 — a deliberate reuse of a documented construction, not a claim of CT protocol compliance), under a fourth domain-separation tag (`pruvz.ai/evidence-log-leaf`); tree heads are periodically signed as checkpoints under a fifth (`pruvz.ai/log-checkpoint`), with a closed member set, batching bounds (`maxLeavesPerCheckpoint` / `maxCheckpointInterval`) and a self-asserted `issuedAt` stated as such. `evidence-log/v1/` is immutable exactly like a released schema directory.
- **Deletion, insertion, reordering and in-place alteration of checkpointed history break proofs**, and the vectors publish one refusal vector for each tamper class, plus wrong tree size, wrong and truncated proof paths, a mutated historical record, tampered and corrupted checkpoint signatures, and malformed documents — every refusal with a stable reason code shared by both runtimes.
- **Stale, forked, rolled-back and wrong-origin checkpoints are refusals** for a verifier that holds accepted-checkpoint state, and growth between accepted checkpoints is believed only with a consistency proof. The vectors publish the acceptance chain and the correctly-signed misbehaving-log candidates that held history must refuse.
- **A hard verification requirement is stated and vectored**: `treeSize` and `rootHash` are one inseparable pair taken from one signed checkpoint, never from the prover — the published proof algorithms admit adjacent-size ambiguity if a prover may state the size independently.
- **Two transport rules are stated exactly, because they decide a refusal code rather than a verdict**: a signature must be *canonical* unpadded base64url — the decoded bytes re-encode to the text received, so one signature has exactly one transported form — and a document that names no format version this implementation speaks, including one that is absent or is not a string, is `UNKNOWN_LOG_VERSION` rather than `LOG_MALFORMED`.
- **The vectors include the published RFC 6962 known-answer test tree**, so both runtimes prove they compute the standard construction rather than a lookalike.
- **A packet still carries no leaf hash, no proof and no checkpoint.** Proofs and checkpoints are fetched from the issuing deployment and checked against the pinned trust registry, exactly like seals; the schema releases are untouched. External anchoring and witnessing remain unimplemented and unclaimed — nothing in this format may be described as anchored, and the `README.md` claims were updated to state exactly what is now implemented and what still is not.
- **Published artifacts are protected from end-of-line conversion** ([`.gitattributes`](.gitattributes)). Every directory that a third party vendors and pins by SHA-256 — [`schema/`](schema/), [`commitment/`](commitment/), [`trust-registry/`](trust-registry/) and [`evidence-log/`](evidence-log/) — is marked `-text`, so a Windows clone and a Linux clone of one release tag produce the same bytes. No released bytes change: the stored blobs were always LF, and what changes is only that a checkout can no longer rewrite them. This was not a precaution — a Windows working copy of [`trust-registry/v1/golden-vectors.json`](trust-registry/v1/golden-vectors.json) had already drifted 1,527 bytes from its published digest.

## 1.4.1 — 2026-08-26

**PATCH** — the packet format is unchanged and packets keep declaring `packetFormatVersion: "1.4.0"`. This release adds a specification, a reference implementation and golden vectors that sit beside the packet format rather than inside it (product PRUVZ-95, signing-key lifecycle and public trust registry).

- **New: the public trust registry specification** — [`docs/TRUST-REGISTRY.md`](docs/TRUST-REGISTRY.md), the reference implementation [`lib/trust-registry.mjs`](lib/trust-registry.mjs) and the published cross-runtime golden vectors [`trust-registry/v1/golden-vectors.json`](trust-registry/v1/golden-vectors.json). It defines a signed, versioned, hash-linked key history: key entries with `use` (`trust-root` or `evidence-signing`, never interchangeable), RFC 7638 thumbprints that are recomputed rather than believed, a closed public-JWK member set that refuses private material outright, a NUL-separated domain-separation header naming the registry format version, and RFC 8785 serialization shared with the commitment layer. `trust-registry/v1/` is immutable exactly like a released schema directory.
- **Bootstrap trust is explicit and mandatory.** Verification requires a pinned `{ issuer, root }` obtained out of band; there is no pinless or permissive mode, because a verifier with no anchor can only believe whatever key history it is handed. A deployment's own API and website are distribution channels and never the root channel.
- **Rotation preserves history; revocation is time-aware.** A seal is judged against the state of its key *at the moment it signed*, not the status the latest manifest declares. A retired key still fully verifies everything it signed while active; a revoked key yields a weakened result before its declared compromise boundary and an invalid one at or after it — and the weakened result says why, because the boundary is compared against a time Pruvz asserted about itself.
- **Rolled-back, forked and substituted key histories are refusals**, with distinct reason codes, including for a stale manifest that is correctly signed and structurally perfect. Verifier state records the `{ issuer, root }` it was established under and may only be continued under that same anchor: two roots are two histories, and their version numbers say nothing about each other.
- **Seal verification is dimensional, never a boolean** — key identity, signature, key lifecycle, subject and content are reported separately, and a result that is `PARTIAL` may never be presented as full verification.
- **A packet still carries no seal, no signature and no trust metadata.** Seals are fetched from the deployment that issued them and checked against a pinned registry; the schema releases are untouched by this release.
- The `README.md` statement that the product "does not implement" signing was corrected: it does, and the packet format's independence from it is stated precisely instead. Append-only inclusion proofs and external anchoring remain unimplemented and unclaimed.

## 1.4.0 — 2026-08-25

**MINOR** — every money value gains its exact decimal representation (product PRUVZ-26, canonical signed evidence representation). Consumers reading `1.3.0` packets keep working on `1.4.0` packets if they ignore fields they do not recognize; `1.4.0` packets do not validate against the `1.3.0` schema (the schemas are strict by design).

- `schema/v1.4.0/` — new format release:
  - `money.amountExact` (new, required string): the amount stated exactly, as canonical decimal text — no exponent, no plus sign, no leading zeros (zero is a bare `0`), no trailing zeros in the fraction, with digit bounds that admit every value the product's exact decimal type can hold. `amount` keeps its meaning and type: the JSON number consumers display. A JSON number is read through IEEE-754 double semantics, which cannot hold every decimal value exactly and need not print identically in every runtime — so the number is what a packet shows and the string is what the amount *is*. Applies everywhere money appears: the decision amount, the expected amount, the observed expected amount, the business discrepancy and both Policy Snapshot amounts.
  - No other field, enum, status, review state, evidence type or trust level changes.
- New packet-level consistency rule for `1.4.0`: a money value's two representations must denote the same amount. Cryptographic commitments bind `amountExact` and never the number, so a packet that displayed one figure and committed another would otherwise satisfy both at once. A new invalid example, `disagreeing-exact-amount.packet.json`, shows the rejection. The rule compares the two numerically — `amount` must be the JSON number a parser produces from `amountExact`, the nearest double to the exact value — so every amount the digit bounds admit stays expressible, including amounts larger than a double can hold exactly.
- **New: the canonical commitment specification** — [`docs/COMMITMENT.md`](docs/COMMITMENT.md), the reference implementation [`lib/canonical.mjs`](lib/canonical.mjs) and the published cross-runtime golden vectors [`commitment/v1/golden-vectors.json`](commitment/v1/golden-vectors.json). It defines how one logical record becomes one deterministic byte string and one digest: a canonical value model that admits only safe integers and commits a number's value rather than its spelling (every precision-sensitive value is normalized text), RFC 8785 serialization, canonical money and UTC-timestamp forms with a closed money member set, a NUL-separated domain-separation header naming the commitment version and record kind (`evidence-item`, `evidence-packet`), the `sha-256` digest suite, and a closed set of refusal codes so two runtimes refuse the same input for the same reason. `commitment/v1/` is immutable exactly like a released schema directory.
- **A packet still carries no commitment.** No signature, no signed manifest, no hash chaining, no external anchor — this release publishes the representation those capabilities will need, and claims nothing more.
- The seven synthetic valid examples now declare format `1.4.0` and carry `amountExact` on every money value; the invalid examples authored against earlier formats keep declaring theirs. The captured conformance packet is unchanged and still declares the format of the run it was captured from. The validator supports all five formats and picks the release matching each packet's declaration.

## 1.3.0 — 2026-08-24

**MINOR** — additive human-triggered re-verification fields (product PRUVZ-51, Customer #1 re-verification after `RESOLVED_EXTERNALLY` with fact supersession). Consumers reading `1.2.0` packets keep working on `1.3.0` packets if they ignore fields they do not recognize and treat the closed enums as open to widening; `1.3.0` packets do not validate against the `1.2.0` schema (the schemas are strict by design).

- `schema/v1.3.0/` — new format release:
  - `evidence.items[].type` gains `FOLLOW_UP_INDEPENDENT_READBACK` (trust `INDEPENDENT_READBACK`): an independent read-back performed during a human-triggered re-verification, after a `RESOLVED_EXTERNALLY` review event.
  - `action.reverificationTiming` (new, nullable object, same shape as `verificationTiming`): the fresh verification window of the latest re-verification, resolved through the same precedence chain but anchored to the moment the correction was reported. Null while no `RESOLVED_EXTERNALLY` event ever triggered one; required (non-null) while `reviewState` is `AWAITING_REVERIFICATION`. `verificationTiming` stays the immutable record of the original window.
  - `action.review.independentlyConfirmed` (new, required boolean): true exactly when Pruvz's own re-verification confirmed the externally-reported resolution and closed the review — the packet's human-resolved versus independently-confirmed-resolved distinction.
  - A `VERIFIED` action may now carry `reviewState: "DECIDED"` and a review block with `independentlyConfirmed: true` (a confirmed external resolution); a first-pass `VERIFIED` still auto-clears to `NOT_REQUIRED` with a null review. No human decision produces `VERIFIED` — only Pruvz's re-verification can.
  - The terminal status taxonomy, review decision vocabulary and trust levels are unchanged.
- New packet-level consistency rules for `1.3.0`: the Worker's re-verification transitions are the only legal gaps in the review-state chain — after a `RESOLVED_EXTERNALLY` decision the review may sit at `DECIDED` (action `VERIFIED`, independently confirmed) or return to `PENDING_REVIEW` (a new non-verified ruling) without a decision entry; `FOLLOW_UP_INDEPENDENT_READBACK` evidence requires a `RESOLVED_EXTERNALLY` decision in the review history and a recorded `reverificationTiming`; a recorded (non-null) `reverificationTiming` itself requires a `RESOLVED_EXTERNALLY` decision — only that event opens a fresh window; `independentlyConfirmed: true` and a review on a `VERIFIED` action both require the latest decision to be `RESOLVED_EXTERNALLY`. Packets of formats `1.2.0` and earlier keep their strict chain rules.
- The five synthetic valid examples now declare format `1.3.0` and carry the new fields; two new examples show the re-verification outcomes: `reverified-confirmed.packet.json` (mismatch → correction reported → follow-up read-back → `VERIFIED`, review `DECIDED`, independently confirmed) and `reverified-mismatch.packet.json` (the reported correction never appeared → `OUTCOME_MISMATCH` again, review back to `PENDING_REVIEW`). A new invalid example, `independently-confirmed-not-verified.packet.json`, shows the marker rejected on a non-verified action. The captured `1.0.0` conformance proof is unchanged. The validator supports all four formats and picks the release matching each packet's declaration.

Consumers reading `1.1.0` packets keep working on `1.2.0` packets if they ignore fields they do not recognize and treat the closed enums as open to widening; `1.2.0` packets do not validate against the `1.1.0` schema (the schemas are strict by design).

- `schema/v1.2.0/` — new format release:
  - `action.reviewState` gains `NEEDS_CORRECTION` and `AWAITING_REVERIFICATION`. A `VERIFICATION_FAILED` action is now under review — it reports a workflow state (`PENDING_REVIEW` first) instead of `NOT_REQUIRED`; `VERIFIED` still auto-clears to `NOT_REQUIRED`.
  - `action.review` (new, nullable object): present exactly for `OUTCOME_MISMATCH` and `VERIFICATION_FAILED` — the review `category` (`BUSINESS_MISMATCH` or `VERIFICATION_FAILURE`, derived from the terminal result), the current `latestDecision` (or `null`) and the complete `decisions` history, one entry per `HUMAN_REVIEW_DECISION` timeline item: `decision` (`APPROVED_EXCEPTION`, `DISMISSED`, `NEEDS_CORRECTION`, `RESOLVED_EXTERNALLY`), `reason`, `reviewerId`, `previousReviewState`, `newReviewState`, the reviewed evidence reference, the decision's own `evidenceId`/`evidenceSequence` and `decidedAtUtc`.
  - The locked review transitions and the category × decision rule (a `VERIFICATION_FAILURE` never admits `APPROVED_EXCEPTION`) are documented in `docs/FIELDS.md`; no review decision can produce `VERIFIED`.
  - The terminal status taxonomy, evidence types and trust levels are unchanged.
- New packet-level consistency rules for `1.2.0`: `review.decisions` lists exactly the timeline's `HUMAN_REVIEW_DECISION` items, in order, each decision's `previousReviewState` continues the previous one's `newReviewState` from `PENDING_REVIEW`; `latestDecision` is the last entry or `null`; `reviewState` equals the latest decision's `newReviewState`, or `PENDING_REVIEW` while no decision was recorded; a `null` review admits no decision evidence. The `1.0.0`/`1.1.0` rule (`DECIDED` ⇔ `HUMAN_REVIEW_DECISION` evidence) still applies to packets of those formats.
- The four synthetic valid examples now declare format `1.2.0` and carry the review block; a fifth example, `verification-failed-resolved-externally.packet.json`, shows a failure review driven through `NEEDS_CORRECTION` and `RESOLVED_EXTERNALLY`. The captured `1.0.0` conformance proof is unchanged. The validator supports all three formats (`1.2.0`, `1.1.0`, `1.0.0`) and picks the release matching each packet's declaration.

## 1.1.0 — 2026-08-17

**MINOR** — additive temporal-verification fields (product PRUVZ-84). Consumers reading `1.0.0` packets keep working on `1.1.0` packets if they ignore fields they do not recognize; `1.1.0` packets do not validate against the `1.0.0` schema (the schemas are strict by design).

- `schema/v1.1.0/` — new format release:
  - `action.verificationTiming` (new, nullable object): the action's frozen verification timing, resolved exactly once at acceptance and never re-resolved — `initialCheckAfterSeconds`, `readbackIntervalSeconds`, `deadlineAtUtc` (null when no deadline was resolved; such an action can never produce a time-based mismatch), `deadlineSource` (`POLICY` → `TENANT_OVERRIDE` → `PRODUCT_SPEC` → `NOT_CONFIGURED`, in resolution precedence order) and `resolvedAtUtc`. Null only on action records that predate the timing model.
  - `action.mismatch.mismatchReason` (new, required in the mismatch block): the temporal mismatch category — `CONTRADICTORY_EVIDENCE` (positive evidence contradicts the claim; assigned immediately) or `EXPECTED_OUTCOME_ABSENT_AFTER_DEADLINE` (the expected outcome never appeared and the resolved deadline passed).
  - `action.policySnapshot.rules.verificationDeadlineSeconds` (new, nullable): the policy's verification deadline, so a `POLICY`-sourced timing resolution is explainable from the packet.
  - `mismatch.reasonCode` known codes gain `REFUND_FAILED` (a matching refund observed in a terminal failed state — contradictory evidence). The field remains an open string by contract.
  - The terminal status taxonomy, review states, evidence types and trust levels are unchanged.
- New packet-level consistency rule: `EXPECTED_OUTCOME_ABSENT_AFTER_DEADLINE` requires a resolved `verificationTiming.deadlineAtUtc`.
- The four synthetic valid examples now declare format `1.1.0` and carry the new fields; the captured `1.0.0` conformance proof is unchanged. The validator supports both formats (`1.1.0`, `1.0.0`) and picks the release matching each packet's declaration.

## 1.0.0 — 2026-08-02

Initial public release of the Public Evidence Packet format.

- `schema/v1.0.0/` — the packet envelope, the action record, and the ordered evidence timeline, mirroring the action details and evidence views of the Pruvz product API. Timestamps require the `Z` UTC designator, matching the `*AtUtc` field names.
- Structural rules enforced beyond field shapes: terminal-status consistency (a `VERIFIED` action carries a final outcome and nothing else; a mismatch carries its dimensions and no fabricated outcome; a technical failure carries its failure block and no business result; a pending action carries nothing terminal), the server-assigned evidence type-to-trust mapping, and the no-fabricated-zero rule for non-evaluable discrepancies.
- Packet-level consistency validation for the cross-object rules JSON Schema cannot express: matching `actionId` between the two parts, unique/ascending/contiguous timeline sequences, unique evidence ids, `DECIDED` ⇔ `HUMAN_REVIEW_DECISION` coupling, and execution-state/timestamp/verification-state agreement.
- Four synthetic valid examples (verified, mismatch with a recorded human review decision, technical verification failure, verification pending) and ten synthetic invalid examples, each with exactly one documented defect.
- Local validator (`npm run validate -- <file>`), packet composer bridging the two saved API responses of a live run into a conforming packet (`npm run compose`, see `docs/CONFORMANCE.md`), and automated tests (`npm test`).
- A captured conformance proof: a packet composed from the two API responses of a real demo run (2026-08-01), validated by the same tests and CI as the authored examples.
